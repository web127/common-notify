# Common-Notify 通知服务设计文档

**日期**: 2026-04-02
**版本**: v1.0 (MVP)

## 1. 问题理解

### 1.1 背景
企业内部多个业务系统在关键事件发生时，需要调用外部系统供应商提供的 HTTP(S) API 进行通知。例如：
- 用户通过第三方广告系统引流并成功注册后，通知对应的广告系统
- 用户订阅付款成功后，通知 CRM 系统更改 Contact 状态
- 用户购买商品后，通知库存系统进行库存变更

### 1.2 核心痛点
- **多供应商异构性**: 不同供应商的 API 地址、Header、Body 格式各不相同
- **重复建设**: 每个业务系统都需要实现类似的通知逻辑
- **可靠性保障**: 业务系统需要自己处理重试、持久化、幂等等可靠性问题

### 1.3 目标
设计并实现一个内部服务，接收业务系统提交的外部 HTTP 通知请求，并尽可能可靠地投递到目标地址。

### 1.4 HTTP 与 HTTPS 的区别及处理

外部供应商可能提供 HTTP 或 HTTPS 两种协议的 API，我们的系统需要支持两者。

| 维度 | HTTP | HTTPS | 对我们系统的影响 |
|------|------|-------|----------------|
| **安全性** | 明文传输，数据可被窃听、篡改 | TLS/SSL 加密传输，安全 | HTTPS 是生产环境推荐方式 |
| **证书** | 不需要证书 | 需要服务器证书 | 需要支持证书验证和跳过验证选项 |
| **端口** | 默认 80 | 默认 443 | 由 URL 指定，无需特殊处理 |
| **性能** | 略高（无加密开销） | 略低（加密/解密开销） | 对 MVP 影响可忽略 |

#### 1.4.1 我们系统需要支持的 HTTPS 配置
- **默认行为**: 验证服务器证书链（生产环境安全推荐）
- **测试环境支持**: 允许跳过 TLS 验证（用于自签名证书）
- **企业内部支持**: 允许配置自定义 CA 证书

#### 1.4.2 与业务系统的关系
- 业务系统无需关心供应商使用 HTTP 还是 HTTPS
- 所有差异由我们的服务在供应商配置层统一处理

## 2. 系统价值与定位

### 2.1 核心价值
**让业务系统专注于业务，而非通知细节！**

### 2.2 为上游屏蔽的复杂性

#### 2.2.1 屏蔽多供应商的异构性
| 复杂性 | 业务系统原本需要做 | 现在只需做 |
|--------|-------------------|-----------|
| **不同API地址** | 维护 N 个供应商的 URL 配置 | 只需指定 `vendor_id` |
| **不同Header格式** | 为每个供应商设置不同的认证、Content-Type 等 | 无需关心，由服务统一处理 |
| **不同Body格式** | 为每个供应商构建不同的请求体结构 | 只需传业务数据 `payload` |
| **不同HTTP方法** | 记住每个供应商用 POST 还是 PUT | 无需关心 |

#### 2.2.2 屏蔽可靠性复杂性
| 复杂性 | 业务系统原本需要做 | 现在只需做 |
|--------|-------------------|-----------|
| **重试逻辑** | 自己实现重试、退避策略 | 发完即忘，服务自动重试 |
| **失败处理** | 处理超时、5xx、网络错误 | 只需查询状态或等待成功 |
| **持久化** | 自己存储待发送通知 | 服务自动持久化 |
| **幂等性** | 自己防重 | 提供 `out_biz_no` 即可 |

#### 2.2.3 屏蔽运维复杂性
| 复杂性 | 业务系统原本需要做 | 现在只需做 |
|--------|-------------------|-----------|
| **监控告警** | 监控通知是否送达 | 统一监控面板 |
| **日志追踪** | 自己记录通知日志 | 统一日志查询 |
| **配置变更** | 供应商URL变更需重新部署 | 后台更新配置即可 |

### 2.4 核心收益
1. **开发效率**: 新业务系统接入只需几行代码，无需关心供应商细节
2. **维护成本**: 供应商变更只需更新配置，无需重新部署业务系统
3. **可靠性**: 统一的重试、持久化、幂等保证，比每个系统自己实现更可靠
4. **可观测性**: 统一的监控、日志、查询界面

## 3. 系统边界

### 3.1 我们解决的问题
- ✅ 接受 HTTP 通知请求从业务系统
- ✅ 持久化存储通知到 SQLite
- ✅ 管理供应商 API 配置（端点、请求头、格式模板）
- ✅ 可靠地投递通知到外部供应商 API，带有重试机制
- ✅ 跟踪投递状态和尝试历史
- ✅ 幂等性保证（通过 out_biz_no）

### 3.2 我们明确不解决的问题（及原因）

| 不解决的问题 | 原因 | 未来可能添加？ |
|------------|------|--------------|
| **认证/授权** | 业务系统是内部的，信任已建立；可以以后添加 | ✅ 可能 |
| **外部 API 限流** | 让供应商处理自己的限流；我们只在 429 时重试 | ✅ 可能 |
| **复杂转换管道** | 保持简单，使用基本的请求头/请求体模板；避免过度设计 | ✅ 可能 |
| **多实例协调** | 对于 MVP，假设单实例；以后可以添加分布式锁 | ✅ 可能 |
| **管理 Web UI** | 管理操作仅通过 API；UI 可以以后添加 | ✅ 可能 |
| **死信队列** | MVP 中不提供；可后续添加 | ✅ 可能 |

## 4. 可靠性与失败处理

### 4.1 投递语义：至少一次 (At-least-once)
- **保证**: 每个通知将至少投递一次
- **重复可能**: 业务系统必须处理幂等性
- **为什么**: 这是 MVP 唯一实际的保证；精确一次需要与供应商系统进行复杂协调

### 4.2 失败处理策略

#### 4.2.1 瞬时失败（5xx、网络错误、超时）
- **重试策略**: 指数退避：1s、2s、4s、8s、16s、32s（最多 6 次）
- **达到最大尝试次数后**: 标记为 "failed"，需要人工干预

#### 4.2.2 永久失败（4xx 除了 429）
- **立即标记为 "failed"**
- **不重试**（客户端错误，需要配置更正）

#### 4.2.3 长期供应商不可用
- 通知保持 "pending" 状态，退避时间递增
- MVP 中没有内置死信队列（以后可以添加）
- 提供管理 API 手动重试或删除失败的通知

#### 4.2.4 我们的服务宕机
- SQLite 提供持久性；所有待处理通知在重启后仍然存在
- Cron 作业在重启后从中断处继续

## 5. 取舍与演进

### 5.1 什么是"过度设计"以及我们为什么不采用

#### 5.1.1 分布式消息队列（RabbitMQ/Kafka）
- **为什么不**: 增加操作复杂度；SQLite + cron 对于中等规模已足够
- **替代方案**: 我们将使用数据库作为队列，这对于 MVP 更简单

#### 5.1.2 微服务架构
- **为什么不**: 单一服务更简单；我们可以在需要时拆分
- **替代方案**: 单体但模块化设计，关注点清晰分离

#### 5.1.3 高级可观测性（分布式追踪、指标管道）
- **为什么不**: 首先使用结构化日志保持可观测性简单
- **替代方案**: 基本日志 + 用于查询状态的管理 API

### 5.2 未来演进（当流量/复杂度增长时）

#### 5.2.1 扩展到高容量
- 用 PostgreSQL 替换 SQLite 以获得更好的写入并发
- 添加 Redis 用于缓存供应商配置和作为缓冲队列
- 引入消息队列（RabbitMQ）进行异步处理

#### 5.2.2 高可用性
- 部署多个实例，为 cron 作业使用分布式锁
- 数据库查询的只读副本
- worker 协调的领导者选举

#### 5.2.3 增强功能
- 为永久失败的通知添加死信队列
- 用于管理和监控的 Web UI
- 用于复杂有效负载的高级转换引擎
- 供应商 API 的限流和断路器

### 5.3 关键判断
- 我们优先考虑 MVP 的简单性和交付速度
- 我们以允许渐进演进的方式构建
- 我们避免过早优化，但留下清晰的扩展点

```
│  业务系统       │

         │ HTTP API
         ▼
┌─────────────────────────────┐
│   API 层 (Gin HTTP Server) │
│  - 接收通知请求             │
│  - 验证请求格式             │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│   服务层                    │
│  - 通知服务                 │
│  - 供应商配置服务           │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│   数据层 (SQLite)           │
│  - 通知表                   │
│  - 供应商配置表             │
└─────────────────────────────┘
           ▲
           │
┌─────────────────────────────┐
│   定时任务 (Cron Worker)    │
│  - 每10秒扫描待发送通知     │
│  - 执行HTTP请求             │
│  - 重试逻辑                 │
└─────────────────────────────┘
```

### 6.2 数据模型

#### 6.2.1 通知表 (notifications)
| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | INTEGER | 主键 |
| `out_biz_no` | VARCHAR | 外部业务单号 (用于幂等) |
| `vendor_id` | VARCHAR | 供应商ID |
| `event_type` | VARCHAR | 事件类型 (如：registration, payment, inventory_change) |
| `payload` | JSON | 请求体内容 |
| `status` | VARCHAR | 状态 (pending, processing, success, failed) |
| `attempts` | INTEGER | 已尝试次数 |
| `last_attempt_at` | TIMESTAMP | 最后尝试时间 |
| `next_attempt_at` | TIMESTAMP | 下次尝试时间 |
| `error_message` | TEXT | 错误信息 |
| `created_at` | TIMESTAMP | 创建时间 |
| `updated_at` | TIMESTAMP | 更新时间 |

**唯一索引**: `(out_biz_no, vendor_id)` - 确保同一业务单号对同一供应商只发送一次

#### 6.2.2 供应商配置表 (vendors)
| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR | 主键 |
| `name` | VARCHAR | 供应商名称 |
| `endpoint_url` | VARCHAR | 目标URL (支持 http:// 和 https://) |
| `method` | VARCHAR | HTTP方法 (POST/PUT等) |
| `headers` | JSON | 请求头 |
| `body_template` | TEXT | 请求体模板 (支持占位符，如 {{.event_type}}, {{.payload}}) |
| `timeout_ms` | INTEGER | 超时时间 |
| `skip_tls_verify` | BOOLEAN | 是否跳过 TLS 证书验证 (默认: false) |
| `ca_cert` | TEXT | 自定义 CA 证书 (PEM 格式，可选) |
| `created_at` | TIMESTAMP | 创建时间 |
| `updated_at` | TIMESTAMP | 更新时间 |

### 6.3 API 设计

#### 6.3.1 提交通知
```
POST /notifications
{
  "out_biz_no": "biz-20240402-12345",
  "vendor_id": "vendor-123",
  "event_type": "registration",
  "payload": {
    "user_id": 123,
    "event": "registration"
  }
}
```

#### 6.3.2 查询通知状态
```
GET /notifications/:id
```

#### 6.3.3 供应商配置管理
```
POST /vendors
GET /vendors/:id
PUT /vendors/:id
DELETE /vendors/:id
```

#### 6.3.4 手动重试失败通知
```
POST /notifications/:id/retry
```

## 7. 关键工程决策

### 7.1 使用 SQLite 作为持久化存储
- **选择原因**: 零配置、单文件、易部署，完全满足 MVP 需求
- **替代方案**: PostgreSQL - 功能更强但需要额外部署和运维

### 7.2 使用 Cron 定时任务作为重试机制
- **选择原因**: 简单可靠，避免引入消息队列的复杂性
- **替代方案**: 内存队列 + 实时 worker - 延迟更低但 crash 时可能丢失内存中的任务

### 7.3 模板化供应商配置
- **选择原因**: 灵活支持不同供应商的 API 格式
- **替代方案**: 硬编码每个供应商的逻辑 - 不够灵活，新增供应商需要改代码

### 7.4 幂等性设计
- **选择原因**: 通过 `out_biz_no` + `vendor_id` 唯一索引实现，业务系统无需担心重复调用
- **关键**: 要求上游业务系统提供幂等键
